# The Monday ritual and idle browsing (journey)

Scope: PRODUCT's two confirmed scenes, followed end to end. Monday: the weekly pushes (`service/WeeklyRecapWorker.kt`, `service/ForgeNotifications.kt`), the feed's coach row (`ui/notifications/`, `data/repo/NotificationFeed.kt`) and the Coach tab (`ui/coach/`). The couch: Stats (`ui/gym/stats/`), Profile BODY and ACTIVITY (`ui/profile/`), Goals (`ui/goals/`) and Recap (`ui/recap/`). 17 raised, 5 kept (5 revised), 12 dropped.

Each screen in this journey has already been audited in this pass, and most of what this finder saw is carried there: the push that lands on Home (RCH-02), Skip with no way back (CCH-01), evidence and verdicts with no numbers (CCH-02, CCH-06), the six-week record (CCH-07), Recap with no door (HOM-01, HOM-10), six-lift Stats and undated charts (STH-01 to STH-03), and the missing bodyweight page (BOD-01). The table at the end points to them. What's left is what only the journey sees, the joins between screens. The bell stops showing an undecided call as soon as Coach is opened. The Monday push never names the change, and on deload weeks it arrives twice. A lift the coach names can't be followed to its history. And two idle-browsing dead ends remain: a weigh-in Stats asks for but can't take, and reached goals with no date.

## Findings

### RIT-02 · An undecided call drops out of the bell the first time Coach is opened
missing-state · impact high · effort M · Notifications feed coach row, Home bell, Coach tab

- **Now:** Every Coach page load calls `coachRepo.markSeen(weekId)` ([CoachViewModel.kt:188-189](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachViewModel.kt#L188-L189)). Tapping the feed row does the same through `markCoachBriefSeen` ([NotificationsScreen.kt:91](../../../forge-android/app/src/main/java/com/forge/app/ui/notifications/NotificationsScreen.kt#L91), [NotificationFeed.kt:416-419](../../../forge-android/app/src/main/java/com/forge/app/data/repo/NotificationFeed.kt#L416-L419)). After that, `pendingBanner()` returns null for the rest of the week ([CoachRepository.kt:1080](../../../forge-android/app/src/main/java/com/forge/app/data/repo/CoachRepository.kt#L1080)) whether or not a decision is still proposed, so the COACH BRIEF row ([NotificationFeed.kt:225-235](../../../forge-android/app/src/main/java/com/forge/app/data/repo/NotificationFeed.kt#L225-L235)) and its bell count disappear. Nothing else says a call is open: Home reads no coach state except the directive, and the bottom bar badges only Academy ([HubScreen.kt:130](../../../forge-android/app/src/main/java/com/forge/app/ui/nav/HubScreen.kt#L130)). When the next Monday's pass runs, any call still open is stamped `skipped` ([CoachDao.kt:123-124](../../../forge-android/app/src/main/java/com/forge/app/data/db/dao/CoachDao.kt#L123-L124)). CCH-01 logs that stamping as an engine bug.
- **Why it matters:** The Monday ritual ends in a decision ([PRODUCT.md:17](../../../PRODUCT.md#L17)). A user who swipes to Coach just to read, or who is interrupted before tapping Apply, leaves with the bell at 0 and no reminder anywhere. A week later the call has lapsed, and the ledger shows it as SKIPPED, a decision the user never made.
- **Proposal:** Split "new" from "open".
  - Leave `pendingBanner()` and `markSeen` unchanged. They still gate the push and the arrival banner, so neither one fires twice.
  - Add `CoachRepository.openCalls()`, which returns the latest pass's week id and its `STATUS_PROPOSED` decisions, with no seen check.
  - In `NotificationFeed`, keep the COACH_BRIEF row while the latest pass has an open call. It keeps the same id, `coach.<weekId>`, so no second arrival banner fires. The title comes from the open calls, using RIT-13's line builder ("Bench Press · 3 → 4 sets", then "+1 more"). The detail is "Week of Sep 28", via `coachWeekLabel`.
  - The row clears when the last call is applied or skipped. Re-read the feed's coach source after `CoachViewModel.act` finishes, or observe the week's decisions from Room.
  - Clear all still removes the row: store a `dismissedOpenCallsWeekId` beside `lastSeenCoachWeekId`, and restore it in the existing Undo lambda ([NotificationFeed.kt:351-358](../../../forge-android/app/src/main/java/com/forge/app/data/repo/NotificationFeed.kt#L351-L358)).
  - Change the kind's explainer from "Each week's read, when it's new" to "Each week's calls, until you decide" ([NotificationFeed.kt:60](../../../forge-android/app/src/main/java/com/forge/app/data/repo/NotificationFeed.kt#L60)).

  Revised: the finder changed `pendingBanner` itself, which would have re-armed the push and the arrival banner. This keeps both to once a week and adds a separate source for the row.
- **Doctrine:** §4.6 sends anything "waiting on you" behind the bell ([DESIGN.md:100](../../../.claude/DESIGN.md#L100)), and an open call is exactly that. It adds no page strip (SETTLED 2026-07-27, [SETTLED.md:85-89](../../../.claude/design/SETTLED.md#L85-L89)), no Coach tab badge and no Home line (SETTLED 2026-08-15 #2: the bell stays the only count, [SETTLED.md:386](../../../.claude/design/SETTLED.md#L386)). "Acting on a row clears it" ([DECISIONS.md:291](../../../.claude/design/DECISIONS.md#L291)) still holds, but the act is now Apply or Skip, not opening the page. The active-session row already stays after it is tapped, and HOM-08 makes the same change for the check-in. Record the change beside SETTLED's 2026-09-01 check-in entry. No area report or prior audit covers this.

### RIT-13 · The Monday push says "Your coach has an update" and never names the change, and deload weeks get two pushes
copy-voice · impact medium · effort S · Coach brief push, deload push

- **Now:** The brief push always has the same title, "Your coach has an update". Its body is `summaryFor`'s stored line, prefix included: "Coach · 2 proposals for this week" ([WeeklyRecapWorker.kt:84-88](../../../forge-android/app/src/main/java/com/forge/app/service/WeeklyRecapWorker.kt#L84-L88), [CoachRepository.kt:1051-1063](../../../forge-android/app/src/main/java/com/forge/app/data/repo/CoachRepository.kt#L1051-L1063)). The feed strips "Coach · " when it renders ([NotificationFeed.kt:232](../../../forge-android/app/src/main/java/com/forge/app/data/repo/NotificationFeed.kt#L232)), but the push keeps it. A hold week pushes "Coach · holding steady this week", and a failed pass pushes "Coach · couldn't run this week", both under "an update". On a deload week, the pass's one call is a deload built from `DeloadAdvisor` ([AutoCoachPlanner.kt:156-168](../../../forge-android/app/src/main/java/com/forge/app/domain/coach/AutoCoachPlanner.kt#L156-L168)). The worker then posts a second push from the same advisor: "Time for a deload week" / "Accumulated fatigue: ..." ([WeeklyRecapWorker.kt:96-103](../../../forge-android/app/src/main/java/com/forge/app/service/WeeklyRecapWorker.kt#L96-L103), [AdaptationRepository.kt:393](../../../forge-android/app/src/main/java/com/forge/app/data/repo/AdaptationRepository.kt#L393)). The tile names a call with a subject and a change ("Bench Press", "3 → 4 sets"). That split comes from `callCopy`, which is internal to `ui/coach` ([CoachCall.kt:44-65](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachCall.kt#L44-L65)).
- **Why it matters:** The push starts the ritual. It never says what changed, so every week's push reads the same, and a hold week gets a push with nothing to act on. On a deload week the shade holds two notifications about one call.
- **Proposal:**
  - Move `CallCopy`/`callCopy` and `coachWeekLabel` to `domain/coach`. They are pure functions, and the UI imports them back.
  - The worker reads `coachRepo.brief()`. The snapshot is cached, and `pendingBanner` has already ensured the pass.
  - **Open calls:** title = the first open call ("Bench Press · 3 → 4 sets"; a deload reads "Deload week"). Body = "+1 more call · week of Sep 28", or the call's humanized reason when it's the only call.
  - **Hold week:** title "No changes this week". Body = `review.focusLine`, the cue CCH-03 puts on the Coach page, so the push and the page agree.
  - **Failed pass:** no push. The feed row still reports it.
  - Skip the separate deload push when the latest pass has an open deload call and the brief push was posted. Keep it when the coach channel is blocked, or when no pass proposed a deload.
  - Build the call line once, and share it with RIT-02's feed row title.

  Revised: the milestone half of the finding is HOM-16 (see the table). The double deload push is new.
- **Doctrine:** PRODUCT voice (binding): generated lines vary with the numbers, and machine identifiers never render ([PRODUCT.md:98-102](../../../PRODUCT.md#L98-L102)). §11 lists notifications among generated lines ([DESIGN.md:265](../../../.claude/DESIGN.md#L265)). FAILURES *Machine leak* covers the stored "Coach ·" prefix ([FAILURES.md:140](../../../.claude/design/FAILURES.md#L140)). No channel, notice kind or notification is added. Quiet hours and the per-channel opt-outs are unchanged. Where a push tap lands is RCH-02, and the reminder and come-back copy is RCH-10.

### RIT-11 · Stats asks for a weigh-in and gives no way to log one, under a title Coach also uses

Logging lives on Profile → BODY → WEIGHT ([ProfileScreen.kt:428-442](../../../forge-android/app/src/main/java/com/forge/app/ui/profile/ProfileScreen.kt#L428-L442)) and in the daily check-in. - **Why it matters:** Onboarding asks for bodyweight only on its optional closing step. A lifter who skipped that step meets this sentence on every Stats visit, and nothing says the fix is on Profile. Two tabs also use one label for two different readings.
- **Proposal:**
  - Rename the Stats section "Relative strength", the code's own name for it ([StatsContent.kt:220](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/stats/StatsContent.kt#L220)). The caption stays.

After a save, the section fills in from the existing `bodyweightPoints` flow.

  Revised: the "Still calibrating" half is STH-08's. The finder's new name, "Strength standards", is dropped, because STH-08 removes the tier standards. And Stats and Coach are not adjacent tabs: Home sits between them ([MAP.md:13](../../../.claude/design/MAP.md#L13)).
- **Doctrine:** §2③ and §8: a do-now action scoped to one row is a whole-row tap with a drawn outlined pill ([DESIGN.md:66](../../../.claude/DESIGN.md#L66), [:209](../../../.claude/DESIGN.md#L209)), the BODY rows' own idiom. FAILURES *Status-word empty* ([FAILURES.md:97](../../../.claude/design/FAILURES.md#L97)): the zero state becomes a row you can act on, not a sentence. Only the log sheet is reused.

### RIT-14 · The coach's lift rows lead nowhere, and their overflow ends on a dead "And N more."
discoverability · impact low · effort S (after STH-01 and STH-02) · Coach > Signals > Lifts on watch (advanced tracking)

- **Now:** Under advanced tracking, each Lifts-on-watch row draws one lift's e1RM sparkline, trend word and figure, and does nothing when tapped ([CoachStand.kt:159-190](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachStand.kt#L159-L190), `LiftTrendRow` at [:274](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachStand.kt#L274)). Past eight lifts the list ends on a muted "And $more more." with no action ([CoachStand.kt:44](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachStand.kt#L44), [:184-187](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachStand.kt#L184-L187)). Each row's `slotId` is the library exercise id ([CoachRepository.kt:988-999](../../../forge-android/app/src/main/java/com/forge/app/data/repo/CoachRepository.kt#L988-L999)), the same id Stats keys lifts by. Stats can open one lift's trend only from inside Stats ([StatsContent.kt:69-70](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/stats/StatsContent.kt#L69-L70), [:149-153](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/stats/StatsContent.kt#L149-L153)), and only for its top six.
- **Why it matters:** While browsing, the stalled or slipping lift the coach just named is the one the user wants to look at, and the trail stops at its sparkline. Getting there today takes two swipes, the Strength lens and a hunt, and it fails for any lift outside Stats' top six.
- **Proposal:** Once STH-01's lift page and STH-02's lift index exist:
  - Each `LiftTrendRow` becomes a whole-row tap, `clickableLabeled("Open <lift>")`, that pushes `Routes.liftDetail(slotId)`.
  - "And N more." becomes `all N lifts →`, opening the lift index. Draw it as a `CoachAction` in onBg, as CCH-07 does for the record.
  - The default view's "Lifts · 2 of 3 climbing" line ([CoachNow.kt:131-164](../../../forge-android/app/src/main/java/com/forge/app/ui/coach/CoachNow.kt#L131-L164)) stays passive. It counts several lifts, so it has no single destination.

  Revised: the finder lifted Stats' `focusLift` up to the hub and swiped over to the Stats tab. That is sibling-tab navigation, and it fails past six lifts. The pushed lift page is the destination instead.
- **Doctrine:** §4.5: a row with a mark answers a tap with detail. §4.2: a data drill-down is navigation in place ([DESIGN.md:96-99](../../../.claude/DESIGN.md#L96-L99)). §12 overflow is a trim plus `view all →`, never a bare count line ([DESIGN.md:306](../../../.claude/DESIGN.md#L306)). §2③: one tap target per row. A pushed Detail route is not the sibling-tab link SETTLED removed (Coach→Academy, [SETTLED.md:94-98](../../../.claude/design/SETTLED.md#L94-L98)). CCH-07 fixes the record's own "And N more weeks." line. This fixes the lifts list's.

### RIT-17 · Reached goals don't say when, and the lens sorts them by the day they were set
feature-gap · impact low · effort M · Goals > Reached lens

- **Now:** The Reached lens sorts by `createdAt`, under a comment that says "newest first, because a finished goal's only remaining question is when" ([GoalsScreen.kt:99-109](../../../forge-android/app/src/main/java/com/forge/app/ui/goals/GoalsScreen.kt#L99-L109)). Every row's caption reads "Reached" ([GoalsComponents.kt:149-157](../../../forge-android/app/src/main/java/com/forge/app/ui/goals/GoalsComponents.kt#L149-L157), [:360](../../../forge-android/app/src/main/java/com/forge/app/ui/goals/GoalsComponents.kt#L360)). Yet the `GoalLens` KDoc calls the lens pill "the only place the word 'reached' is said on a populated screen" ([GoalsScreen.kt:229-232](../../../forge-android/app/src/main/java/com/forge/app/ui/goals/GoalsScreen.kt#L229-L232)), and SETTLED says the lens "says it once for a whole list instead of once per row" ([SETTLED.md:520-523](../../../.claude/design/SETTLED.md#L520-L523)). `GoalProgress` carries no reached date ([GoalRepository.kt:46-56](../../../forge-android/app/src/main/java/com/forge/app/data/repo/GoalRepository.kt#L46-L56)).
- **Why it matters:** For a long-time user, the Reached lens is the record of what they hit. Today it is a column of names, each stamped with the same word, in the order the goals were typed in.
- **Proposal:** Add `reachedAt: Long?` to both progress types.
  - **Lift target:** the first finished session with a qualifying set at or above the target, on or after `createdAt`. If the best set had already cleared it, use `createdAt` (reached on save). This is one sibling query of `maxWeightPerExercise`, taking `MIN(sess.started_at)` with the same filters ([LoggedSetDao.kt:214-223](../../../forge-android/app/src/main/java/com/forge/app/data/db/dao/LoggedSetDao.kt#L214-L223)).
  - **Bodyweight goal:** the first weigh-in at or past the target since `createdAt`.
  - **All-time totals:** the session or cardio entry at which the running total crossed the target. These count from the first log, not from `createdAt` ([ExtendedGoalRepository.kt:179](../../../forge-android/app/src/main/java/com/forge/app/data/repo/ExtendedGoalRepository.kt#L179)).
  - **Weekly and monthly goals** are reached only for the current window. They keep their window caption and sort last.
  - Inside the Reached lens, the caption swaps the repeated word for the reading: "MAR 3 · 11 WEEKS", counting weeks from `createdAt`. A goal reached on save shows only the date. Home, Cardio and Profile keep the word, as "REACHED · MAR 3".
  - Sort the lens by `reachedAt`, newest first.

  Revised: the finder kept "REACHED" in the lens caption, which repeats the lens pill on every row. The date rule is now set per goal kind.
- **Doctrine:** SETTLED Goals 2026-08-23: the caption stays one line under the meter, and the lens says "reached" once. §12: collapse repetition ([DESIGN.md:318](../../../.claude/DESIGN.md#L318)). This is not the rate, ETA or verdict SETTLED defers behind its data gate ([SETTLED.md:561-567](../../../.claude/design/SETTLED.md#L561-L567)): these are past dates, not a projection. §11: the date is a fact the data supports, and nothing praises it. No gamification surface is added.
