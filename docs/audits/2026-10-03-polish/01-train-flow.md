# Train: day list, warm-up and live-session shell

Scope: the hidden Gym day list, the warm-up, the live session's hero, ordering and time-fit slots, its dialogs and long-press menu, and the session ViewModel flows (`ui/gym/train/*.kt` outside `components/`, plus `ui/gym/train/state/`). 15 raised, 13 kept (10 revised), 2 dropped.

The set-logging loop holds up after the 2026-09-26 fixes. The debt is at the edges of a session. Getting in: a phone user can only start the gym day Home picks, and the warm-up neither names the day nor shows a way back. Before the first set, the time fit asks for minutes without saying what the day costs, the engine reorders the day without saying so, and session type has no control even though the engine acts on it. Getting out: finishing early and discarding are each one tap from permanent, and neither says what will be lost. SETTLED lists the live-session screen as untouchable ([SETTLED.md:138](../../../.claude/design/SETTLED.md#L138)), so every item that changes what that screen draws (TRF-03, 06, 07, 08, 12, 15) needs Antho's sign-off. The rest are ViewModel flows, dialogs, copy, or changes on other screens.

## Findings

### TRF-01 · You can only train the day Home picks; the day list is unreachable
discoverability · impact high · effort M · Home Start session and Plan, program view

- **Now:** `DayListScreen` is mounted only as the Stats page, with `initialTab = 1` ([HubScreen.kt:168](../../../forge-android/app/src/main/java/com/forge/app/ui/nav/HubScreen.kt#L168)), so its `TrainTab` "Pick your day." list never renders ([DayListScreen.kt:99](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayListScreen.kt#L99), [DayListScreen.kt:180](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayListScreen.kt#L180)). Every phone route into `GYM_DAY` starts a day the app chose. Home's hero uses `resumeKey ?: directive?.dayKey ?: state.nextUpDayKey` ([OverviewScreen.kt:496](../../../forge-android/app/src/main/java/com/forge/app/ui/overview/OverviewScreen.kt#L496)). The widget ([ForgeNavHost.kt:147](../../../forge-android/app/src/main/java/com/forge/app/ui/nav/ForgeNavHost.kt#L147)) and the feed's resume row ([ForgeNavHost.kt:373](../../../forge-android/app/src/main/java/com/forge/app/ui/nav/ForgeNavHost.kt#L373)) do the same. Home's week strip is passive. Home's Plan opens the program read-only, and that screen's bottom bar shows only in edit mode ([ProgramBuilderScreen.kt:209](../../../forge-android/app/src/main/java/com/forge/app/ui/programbuilder/ProgramBuilderScreen.kt#L209)), so it has no start action. The wear module has no day choice either. Two strings still point at the old list: Settings > About's "Long-press a day on the Gym list" ([SettingsAboutPage.kt:118](../../../forge-android/app/src/main/java/com/forge/app/ui/settings/SettingsAboutPage.kt#L118)) and the leave dialog's "Resume this workout later from its day" ([DayDialogs.kt:44](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayDialogs.kt#L44)).
- **Why it matters:** A lifter whose legs are sore, or whose squat rack is taken, can't do Push instead of the Legs day Home chose. The only workarounds are editing the weekly schedule or opening freestyle, and freestyle loses the program's targets, progression and warm-up. Both prior audits treat the Train tab as dead code to delete ([gym-ui.md cleanup 1](../2026-09-12/gym-ui.md), [01-gym-train.md P3](../2026-09-26/01-gym-train.md)). Neither notes that deleting it removes the last way to pick a day.
- **Proposal:** In `ProgramBuilderScreen`'s view mode, use the empty `bottomBar` slot for one page-end `ForgePrimaryCapsule`, "Train <day name>". It targets the day `WeekBarRail` has selected (`openDay`) and calls a new `onStartDay(dayKey)`, which `ForgeNavHost` wires to `nav.navigateToGymDay`. Hide it for cardio day keys. If a different day is already in progress, the existing `CrossDaySessionDialog` takes over. Then delete `TrainTab` and `DayListViewModel` as the prior audits ask, drop the About row and reword the leave dialog (TRF-04). Two parts of the original finding are dropped. Day colour is not orphaned: the builder's day detail has a colour row ([ProgramBuilderDayDetail.kt:235](../../../forge-android/app/src/main/java/com/forge/app/ui/programbuilder/ProgramBuilderDayDetail.kt#L235)). Single-day re-roll doesn't need a new home either, because Settings > Program already has whole-program re-roll.
- **Doctrine:** §8 allows one filled capsule per page, at the end. View mode has no other action, so this is not a button wall. SETTLED 2026-08-16 removed Home's tiles, not day choice, and nothing in SETTLED, MAP or DECISIONS records removing day choice on purpose. Home's hero still follows the coach (SETTLED 2026-08-16); this is an explicit override on a secondary screen. `WeekBarRail` stays the page's one mark. The program view is not the untouchable live screen.

### TRF-02 · FINISH ends a half-done workout in one tap, with no check and no way back
ux-friction · impact medium · effort S · Live session hero FINISH pill

- **Now:** The accent FINISH pill sits in the hero row next to the date pill and the note glyph, and tapping it dispatches `FinishWorkout` straight away ([DaySessionContent.kt:487](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L487)). `finishWorkout` stops only for an empty session ([DaySessionHandlers.kt:162](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L162)). With 1 of 6 exercises done, it still runs `finishSession`, stops the service, mirrors to Health Connect and evaluates trophies ([DaySessionHandlers.kt:178](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L178)). The summary sheet blocks swipe-dismiss and offers only Complete ([SessionSummarySheet.kt:61](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/components/SessionSummarySheet.kt#L61)), so there is no way back into the workout. The card's own "FINISH WORKOUT →" appears only once nothing else needs work ([DaySessionContent.kt:292](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L292)). The code calls the hero pill "the deliberate finish-anyway" ([DaySessionContent.kt:274](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L274)), but nothing on screen tells a deliberate finish from a stray tap. Keep-screen-on defaults to on, so the screen stays live in a pocket.
- **Why it matters:** One stray tap ends the session for good. History, rotation and the summary's completion read all record a short session. The rest of the workout can only be logged as a separate freestyle session.
- **Proposal:** In `finishWorkout`, after the empty check, collect `exercises.filter { !it.isComplete }`. If any remain, raise a confirm dialog in `LeaveSessionDialog`'s pattern that states the consequence in real numbers: "3 exercises not done · Rows at 1 of 3 sets. Finishing saves the workout as it is." Offer a filled "Finish workout" and a text "Keep going". When nothing remains, FINISH stays one tap. Dropped from the original: renaming the summary's Complete button.
- **Doctrine:** §12 allows a dialog for an irreversible act, provided it words the consequence ([DESIGN.md:323](../../../.claude/DESIGN.md#L323)). Finishing has no undo, and its side effects reach Health Connect and trophies. DECISIONS 2026-07-27 says a dialog is for a decision the app can't proceed without ([DECISIONS.md:367](../../../.claude/design/DECISIONS.md#L367)). The dialog fires only in the exception case. This is a ViewModel flow plus an existing dialog pattern, so the live layout doesn't change.

### TRF-03 · Session type (Technique, Test) has no control, though the coach acts on it
feature-gap · impact medium · effort S · Live session, after Start lifting and before the first set

- **Now:** `SetSessionType` is handled ([DaySessionHandlers.kt:40](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L40)), but nothing in the app or wear module dispatches it. `SessionType`'s KDoc says "TEST / TECHNIQUE have no writer yet (no session-type picker exists)" ([SessionType.kt:11](../../../forge-android/app/src/main/java/com/forge/app/domain/session/SessionType.kt#L11)). The only writer is the automatic NORMAL / FIRST_BACK tag at session start ([WorkoutRepository.kt:183](../../../forge-android/app/src/main/java/com/forge/app/data/repo/WorkoutRepository.kt#L183)). The engine reads the tag: `EXCLUDED_FROM_PROGRESSION` keeps TEST and TECHNIQUE bouts out of progression, plateau and fatigue reads ([AdaptationSnapshot.kt:157](../../../forge-android/app/src/main/java/com/forge/app/domain/adapt/AdaptationSnapshot.kt#L157)). Coach v3 A1 shipped a picker on session detail. SETTLED 2026-09-26 removed it at Antho's request, saying "the in-session type tag (`DaySessionHandlers`) is unaffected" ([SETTLED.md:39](../../../.claude/design/SETTLED.md#L39)), but that tag has never had a control. FEATURES.md still lists session types as shipped ([FEATURES.md:19](../../../.claude/FEATURES.md#L19)).
- **Why it matters:** A 1RM test day or a deliberately light technique day counts as ordinary training. The coach can then see a stall or a jump that never happened and propose a deload or progression from it. The user has no way to say "this one doesn't count".
- **Proposal:** This needs Antho's decision first, because the SETTLED removal may have meant "no session types at all". If he wants the tag, add one `SegmentPill` row, "Normal · Technique · Test", under a mono `SESSION` label. It goes in the pre-first-set slot beside the time fit, after Start lifting and never on the warm-up page, and dispatches `SetSessionType`. A FIRST_BACK session lights no pill and shows one caption of 12 words or fewer naming the automatic tag. Untracked stays out of the row. If he doesn't want it, trim TEST and TECHNIQUE as `SessionType`'s KDoc offers, delete the dead event, and correct the SETTLED line and FEATURES.md. Revised from the original, which also drew the row on the warm-up.
- **Doctrine:** SETTLED 2026-09-26 removed only the session-detail retro-tag and named the in-session tag as kept. A selection is a `SegmentPill`, not buttons (§2③). The row classifies the session for the engine, so it is not a mood or subjective driver (SETTLED). Nothing waits on it and the default is Normal, so it is not a gate. Keeping it off the warm-up preserves SETTLED's one-screen, one-button warm-up. It adds a row to the untouchable screen, so it needs owner sign-off.

### TRF-04 · Leave and cross-day discard delete a workout without saying how much
ux-friction · impact medium · effort S · "Leave this workout?" and "<Day> in progress" dialogs

- **Now:** "Leave this workout?" says "Your logged sets are saved. Resume this workout later from its day, or discard what you've logged." Discard is a plain TextButton next to Keep going ([DayDialogs.kt:43](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayDialogs.kt#L43)), and it cascade-deletes the session at once ([DaySessionHandlers.kt:339](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L339)). In the cross-day dialog, "Discard & start <day>" deletes the other day's whole session the same way ([DayDialogs.kt:71](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayDialogs.kt#L71), [DaySessionHandlers.kt:379](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L379)). Neither dialog gives a count. "From its day" points at the unreachable list (TRF-01); what Home actually shows is Resume session ([OverviewScreen.kt:511](../../../forge-android/app/src/main/java/com/forge/app/ui/overview/OverviewScreen.kt#L511)). The dismiss slot wraps Discard and Keep going in a fixed `Row` ([DayDialogs.kt:47](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayDialogs.kt#L47)), so the three buttons can't reflow at 200%.
- **Why it matters:** Back plus one wrong tap deletes, say, 18 sets with no undo, and nothing says how much is about to go. On the cross-day path, the lifter may not remember that the other session has work in it.
- **Proposal:** Put the number in both the body and the button, using data already on hand. Leave dialog: "18 sets across 5 exercises are saved. Home shows Resume session.", with the button "Discard 18 sets". Cross-day dialog: add a set count to `CrossDaySessionInfo` ([DayUiState.kt:15](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/state/DayUiState.kt#L15)), read with `workoutRepo.allSetsForSession(active.id)` where it is built ([DayViewModel.kt:198](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayViewModel.kt#L198)), and label the button "Discard Pull B's 12 sets". Tint both discards `error`. Drop the inner `Row` so the slot can wrap.
- **Doctrine:** §12 says a destructive dialog words the consequence. §8 says destructive is level ② tinted `error`, never filled red. No new dialog is added, and DECISIONS 2026-07-27 keeps the discard guard. §11 calls for specific numbers and no em dashes. The change is copy plus one data field.

### TRF-06 · The time fit never says how long the day is, and offers choices that do nothing
ux-friction · impact medium · effort S · "Short on time?" row, warm-up and pre-first-set

- **Now:** `TimeFitRow` always offers 15, 20, 30, 45 and 60 minutes ([DayTimeFit.kt:23](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayTimeFit.kt#L23)) and never says how long the remaining work is expected to take. `SessionAdaptor.TimedExercise.seconds` already prices exactly that ([SessionAdaptor.kt:39](../../../forge-android/app/src/main/java/com/forge/app/domain/coach/SessionAdaptor.kt#L39)), and `applyFitToTime` already builds the list ([DaySessionHandlers.kt:83](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L83)). Any choice longer than the day just prints "All of it fits in 60 minutes." ([DayTimeFit.kt:35](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayTimeFit.kt#L35)). The caption, "Say how long you have. Avex keeps the work that matters most and skips the rest." ([DayTimeFit.kt:53](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayTimeFit.kt#L53)), has the app naming itself.
- **Why it matters:** You can't tell whether you're short on time without knowing what the full day costs, so users guess. On a 40-minute day, two of the five chips do nothing.
- **Proposal:** In the ViewModel, sum `seconds` over the same `TimedExercise` list, round to whole minutes, and show the result as the label's reading: `SHORT ON TIME? · ~52 MIN`. Draw only the choices below that figure. A day under 15 minutes draws no row. Replace the caption with "Pick how long you have. Accessories go first, main lifts stay." Dropped from the original: moving the row above the warm-up. The row already reappears under the hero after Start lifting, until the first set ([DaySessionContent.kt:239](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L239)), so nobody misses it.
- **Doctrine:** §4.9 puts the reading beside the control. §2③ says a control that can't run is not drawn. §4.3: the one caption is replaced, not added to. PRODUCT voice: the app never names itself. SETTLED's warm-up entry bans a time estimate on the warm-up ([SETTLED.md:64](../../../.claude/design/SETTLED.md#L64)). MAP's reason for that ban is "a number with no decision attached". This figure is the day's length and the reading for the fit decision, but the row also renders on the warm-up page, so confirm with Antho.

### TRF-07 · The warm-up has no back arrow and never names the day
consistency · impact medium · effort S · Warm-up screen

- **Now:** Until Start lifting, `DayContent` draws only `WarmupFlow` and the time fit ([DaySessionContent.kt:167](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L167)). `SessionHero`, which carries the back arrow and the day name, appears only after that ([DaySessionContent.kt:458](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L458)). `WarmupFlow` opens on a bare `WARM-UP` header; its own comment reads "The gate draws with no top bar above it" ([WarmupFlow.kt:69](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/components/WarmupFlow.kt#L69)). The `warmup.png` golden shows exactly that. The only way out is the system back gesture.
- **Why it matters:** The warm-up is the first screen of most sessions. If Home opened the wrong day, the drills are the only clue, and there's no visible way out.
- **Proposal:** During the warm-up phase, draw `ForgeTopBar(onBack = { onEvent(RequestBack) })` above `WarmupFlow`, and put the day in the anchor: `EditorialHeader(label = "Warm-up · ${state.displayName}")`. Drop `WarmupFlow`'s 24dp status-bar spacer, and re-record the six warm-up goldens. Dropped from the original: the claim that this is the only routed screen without a back arrow, which couldn't be verified.
- **Doctrine:** §4.6: one top-bar back arrow, and never the screen's own name in the bar ([DESIGN.md:100](../../../.claude/DESIGN.md#L100)). The day name goes in the content anchor instead. SETTLED's warm-up entry still holds: one screen and one button, no stepper, no estimate. A back arrow is chrome, not a second action. The warm-up is part of the untouchable `GYM_DAY` screen, so this needs owner sign-off.

### TRF-08 · The engine reorders the day silently, with no note and no way back
ux-friction · impact medium · effort S · Live session, before the first set

- **Now:** When the day's order hasn't been customised, `computeOrderingSuggestion` applies `OrderingAdvisor`'s order without asking ([DayViewModelRefresh.kt:219](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayViewModelRefresh.kt#L219)). A single same-muscle adjacency is enough to trigger it (`orderingMinAdjacencies = 1`), and a priority muscle can jump to the front of the compound block. Nothing on screen says the order changed or why, and nothing restores the plan's order. On a customised day, the same suggestion shows as a SUGGESTED ORDER block with Apply and Dismiss ([DaySessionContent.kt:193](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L193)). That block's label sets 9sp at the call site ([DaySessionContent.kt:200](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L200)), and its reason uses muted at 0.8 ([DaySessionContent.kt:208](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L208)), which is off the §5 ladder.
- **Why it matters:** The program screen lists Bench, Incline, Overhead press, and the session opens on Bench, Overhead press, Incline with no reason given. It reads as a bug, and the lifter can't put it back.
- **Proposal:** When the order is applied automatically, keep the suggestion in state as `autoApplied`. Until the first set, draw a note in the existing ordering slot: one mono `ORDER CHANGED` line, the advisor's reason as the single caption, and an `Undo` `ForgeChromeButton`. Undo restores the plan order and calls `adaptationRepo.logAdviceDismissed(id)`, as Dismiss does, so the cooldown applies. Snap the existing block's label to `labelSmall` with no `fontSize`, and its reason to the 0.65 rung. Dropped from the original: "the warm-up now follows the new first lift". The drills come from the muscles trained, not the order, and the first-lift ramp isn't drawn at all (2026-09-26 audit, P3).
- **Doctrine:** PRODUCT principle 1 says consent stays reversible. §12 prefers undo over confirm. The automatic apply stays, and no prompt is added. The note sits on the element it describes and goes away at the first set, so it isn't a resident page strip (§4.6). It also follows the §5 alpha ladder and §6's ban on call-site `fontSize`. It draws in an existing slot on the untouchable screen, so it needs owner sign-off.

### TRF-09 · Swapping after one logged set dead-ends at "delete your sets first"
ux-friction · impact medium · effort M · Exercise card SWAP once a set exists

- **Now:** Once a set exists, `OpenSwapPicker` just sends "Can't swap after logging sets — delete this exercise's sets first." ([DaySwapHandlers.kt:17](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySwapHandlers.kt#L17), [DaySwapHandlers.kt:56](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySwapHandlers.kt#L56)). Refusing the re-key is right (#11). But the only way forward the message offers destroys logged work, and the engine's own comment describes the better move: "finish that exercise short and substitute the NEXT one" ([SessionAdaptor.kt:113](../../../forge-android/app/src/main/java/com/forge/app/domain/coach/SessionAdaptor.kt#L113)). The ViewModel already has both halves, `AddUnplannedExercise` and `FinishExerciseEarly` ([DayExerciseHandlers.kt:185](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayExerciseHandlers.kt#L185), [DayExerciseHandlers.kt:233](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayExerciseHandlers.kt#L233)). Doing it by hand today means "Done with this exercise", then Up Next's add, whose list holds only program moves (TRL-16 in [02-train-logging.md](02-train-logging.md)).
- **Why it matters:** Bench pinches a shoulder on set 1, or someone takes the bench. The lifter is told to delete the set they just did. Most will keep benching, or log dumbbell press as bench sets, which corrupts the history of both lifts.

The commit runs `FinishExerciseEarly(id)`, then calls `addExerciseToSession` with the picked library id, then focuses the new card. `Program.exercise` already resolves library ids ([Program.kt:359](../../../forge-android/app/src/main/java/com/forge/app/program/Program.kt#L359)). The new row lands at the end of the list, because `effectivePlanForSession` appends extras ([ProgramCustomizationRepository.kt:144](../../../forge-android/app/src/main/java/com/forge/app/data/repo/ProgramCustomizationRepository.kt#L144)), but that doesn't matter because it gets focus straight away. A persistent-scope pick also saves the swap for future sessions, as it does today. Rewrite the message without the em dash for the refusal case that remains (a wrist set landing while the sheet is open).
- **Doctrine:** This reuses the swap picker as it stands (SETTLED 2026-08-23 and 2026-08-24: one accent confirm at the end, no search, no `why` prose) and changes only what the confirm does. Logged sets are never re-keyed, so #11 holds. No new sheet or dialog. §11 bans em dashes, and this one is already on the 2026-09-26 audit's doctrine-debt list.

### TRF-12 · A day with no exercises opens to a blank session with no way to add one
missing-state · impact low · effort S · Warm-up and live session for an empty day

- **Now:** The program builder saves a day with no exercises. `save` has no check ([ProgramBuilderViewModel.kt:391](../../../forge-android/app/src/main/java/com/forge/app/ui/programbuilder/ProgramBuilderViewModel.kt#L391)), and the day editor itself says "No exercises yet" ([ProgramBuilderDayDetail.kt:260](../../../forge-android/app/src/main/java/com/forge/app/ui/programbuilder/ProgramBuilderDayDetail.kt#L260)). Opening that day shows a warm-up with only its header and Start lifting, because `rebuildWarmupProtocol` returns early on an empty list ([DayWarmupBuilder.kt:18](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayWarmupBuilder.kt#L18)). After Start lifting, the hero sits over a blank page. The current card, Up Next and Up Next's add entry are all inside `if (shownExercise != null)` ([DaySessionContent.kt:243](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L243)), and the time fit needs exercises ([DayTimeFit.kt:30](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayTimeFit.kt#L30)). FINISH then lands on "Nothing logged yet".
- **Why it matters:** A custom-plan user who saved a day to fill in later gets a session screen that looks broken, with no way to add the exercise they came to do.
- **Proposal:** When loading finishes with no exercises, skip the warm-up (set `isWarmupComplete`). Draw one `InlineEmptyHint`, "This day has no exercises yet.", over a `ForgePrimaryCapsule` "Add an exercise" that dispatches `OpenAddExercisePicker`. It works best paired with TRL-16's library picker.
- **Doctrine:** §12 says every zero state is drawn. `InlineEmptyHint` is the sanctioned last resort when there's no zero-shaped mark ([DESIGN.md:322](../../../.claude/DESIGN.md#L322)), paired here with one filled action (§8). The populated live layout doesn't change, but this is still a new state on the untouchable screen, so it needs sign-off.

### TRF-13 · A warm-up opt-out can last a week, with no undo and nothing showing it's on
ux-friction · impact low · effort S · Warm-up NOT TODAY / NOT THIS WEEK

- **Now:** Both chips write `warmupDisabledUntilMs` and start the session ([DayWarmupHandlers.kt:24](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayWarmupHandlers.kt#L24)). No snackbar follows, and no Settings row reads or resets the pref; the only reader is session start ([DaySessionHandlers.kt:405](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionHandlers.kt#L405)). Later sessions skip the warm-up silently until the cutoff. Both chip labels are mono uppercase inside buttons ([WarmupFlow.kt:98](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/components/WarmupFlow.kt#L98)).
- **Why it matters:** One tap on the wrong chip turns the warm-up off for up to seven days. The screen that offered the chip no longer appears, so it can't be undone there.
- **Proposal:** After either opt-out, call `SnackbarController.showUndo("Warm-up off until Monday")` (or "until tomorrow"). Undo restores the previous value. Relabel the chips "Not today" and "Not this week". Two related problems belong on the bug list, not in this pass: the handlers use `LocalDate.now()` instead of the injected clock (2026-09-26 audit, P4), and "this week" always ends on Monday whatever Settings > Week starts says.
- **Doctrine:** MAP keeps both chips as the persistent opt-outs ([MAP.md:840](../../../.claude/design/MAP.md#L840)), and SETTLED forbids a second start button. This changes neither. §12 prefers undo over confirm, through §8's single `SnackbarController`. §11 puts buttons in sentence case.

### TRF-14 · The long-press exercise menu repeats the card's chips and says "Toggle skip"
consistency · impact low · effort S · Exercise card long-press; Settings > About gestures

- **Now:** Long-pressing the card opens an `AlertDialog` used as a menu, with "Toggle skip" (which doesn't say which way it will go) and "Open swap picker" ([DayScreen.kt:263](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayScreen.kt#L263)). The card footer already has SWAP and SKIP / UN-SKIP chips ([ExerciseCardComponents.kt:482](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/components/ExerciseCardComponents.kt#L482)). Settings > About still advertises "Skip it, swap it, or set its rest timer" ([SettingsAboutPage.kt:114](../../../forge-android/app/src/main/java/com/forge/app/ui/settings/SettingsAboutPage.kt#L114)), but the rest-timer row has been removed ([DayScreen.kt:270](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DayScreen.kt#L270)).
- **Why it matters:** There are two routes to the same two actions, one of them with developer-style labels. And the only written guide to the gesture promises an action that no longer exists.
- **Proposal:** Delete the quick-actions dialog, `LongPressExercise`, `quickActionsForExerciseId` and the `onLongPress` wiring, so the chips are the one place for these actions. Passing `onLongPress = null` also removes the whole-card `combinedClickable(onClick = {})` that the 2026-09-26 audit flagged as a nested tap ([01-gym-train.md P3](../2026-09-26/01-gym-train.md)). Drop the About row.
- **Doctrine:** §4.3 gives an action one home. DECISIONS 2026-07-27 says a dialog is for a decision, not a menu. Both actions stay one tap away on the card. This only removes chrome.

### TRF-15 · The beat-last-session line uses a ⚡ and the reserved △ LAST green
copy-voice · impact low · effort S · Live session hero, ghost line

- **Now:** When the session is ahead, the hero reads "⚡ BEATING LAST SESSION" in `ForgeLastGreen`, with `fontSize = 9.sp` set at the call site, and the count beside it is drawn the same way ([DaySessionContent.kt:502](../../../forge-android/app/src/main/java/com/forge/app/ui/gym/train/DaySessionContent.kt#L502)). ⚡ isn't one of the app's glyphs, and §5 reserves that green for △ LAST.
- **Why it matters:** It puts an emoji and a borrowed status colour on the one surface where colour has to carry a single meaning. Green on this screen already means "beat last time" on a set row and, per TRL-08, "rest done" on the timer. This line adds a third meaning.
- **Proposal:** Drop the ⚡. When ahead, render "AHEAD OF LAST SESSION · 7 / 10 SETS" in onBackground; otherwise render "VS LAST SESSION · 4 / 10 SETS" in muted. Use `labelSmall` with no `fontSize` override.
- **Doctrine:** §8 bans decorative emoji; the app's glyphs are `→ ↑ ↓ △ • ·` ([DESIGN.md:232](../../../.claude/DESIGN.md#L232)). §5 reserves the colour ([DESIGN.md:143](../../../.claude/DESIGN.md#L143)). §6 and §14 ban call-site `fontSize`, and §11 sets the voice. Only the copy and colour of an existing line change. SETTLED removed the ghost from the session summary, not this live line.
