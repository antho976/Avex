# Fixes, 2026-11-18: cold start

Against `BASELINE-2026-11-18.md`, same phone (Galaxy S21 Ultra, Android 15), same `perf` build
type, same installed data.

## Result

Interleaved A/B: the baseline APK and the fixed APK installed over each other on the same data,
base, new, base, new, 8 cold starts a round, 16 each. Raw runs: `raw/coldstart-ab-*.json`.
Milliseconds after the process starts; `system.*` from the launch intent.

| Milestone | Before p50 | p95 | After p50 | p95 |
|---|---|---|---|---|
| **Home fully loaded** | **295** | 305 | **134** | 146 |
| **Fully drawn**, `system.fullyDrawn` | **359** | 372 | **231** | 261 |
| First frame shown, `system.displayed` | 206 | 221 | 231 | 261 |
| Home composed | 122 | 132 | 101 | 108 |
| Launch settled (splash gone) | 438 | 449 | 380 | 383 |

**On screen** (5 recordings each, tap to the last visible change): before 461 to 933, median
**524 ms**; after 446, 449, 451, 458, 491, median **451 ms**.

The first frame is 25 ms later on purpose: the splash is now held until Home is loaded, so the
first frame a person sees and the fully drawn frame are the same frame. Before, there were 150 ms
between them, and that gap was on screen: `raw/launch-before-after-2026-11-18.png` shows the old
launch reading "Upper A / Start session" at 260 ms and correcting itself until 460 ms, and the new
one uncovering the finished page at about 300 ms.

The build as committed (the A/B build minus the snapshot warm-up, see "Tried and removed"), 8
cold starts, `raw/coldstart-final-2026-11-18.json`: Home fully loaded 132, fully drawn 228,
settled 374.

Of the 451 ms that remain on screen, roughly 185 ms is the launcher's own open animation, 90 ms is
the system handing the splash over for its exit, and 150 ms is the fade.

## What was changed, in the order it was measured

Each step is 12 cold starts on the build with that step added. The first two rows ran on an
install whose history had been cleared (see "A lost data set"), so read them against each other
only; the A/B above is the result.

| Step | Home fully loaded p50 | Fully drawn p50 | Settled p50 |
|---|---|---|---|
| Settings read at process start, first composition seeded from it | 311 | 381 | 452 |
| `ConflatedRefresh`: no 100 ms debounce | 175 | 248 | 441 |
| Splash held for Home's load; fade 120 ms; no root fade, no Home rise | 143 | 247 | 359 |
| Home composed inside `onCreate` when the settings are already in memory | 140 | 246 | 356 |
| Home's reads start at view-model creation, off the main thread | 129 | 226 | 340 |

The fade then went from 120 ms to the Fast token (150), which is why the A/B settles at 380.

1. **`ConflatedRefresh` no longer waits 100 ms** (`core/ConflatedRefresh.kt`). The debounce is
   replaced by one turn of the dispatcher, which collapses the same bursts. This is the fix that
   mattered: 311 to 175. `ConflatedRefreshTest` asserts the first read starts with no time passing,
   which is the guard against it coming back. It also speeds up Stats' body lens, which uses the
   same helper (not measured).
2. **The hand-off** (`ui/launch/LaunchHandOff.kt`, `MainActivity`, `ForgeNavHost`,
   `OverviewScreen`). Home tells the Activity when its first load is in; the splash waits for that,
   at most 250 ms. Design decision recorded in `.claude/design/DECISIONS.md`.
3. **Home's reads start with its view model** (`OverviewViewModel`): the directive, coach row and
   body readings at creation and on background threads, and the three shared flows are subscribed
   to for a moment so their queries start then too. The screen's first resume no longer triggers a
   second read.
4. **Settings** (`ForgeApp`, `SettingsRepository`, `ForgeUiSettings`, `MainActivity`). The file is
   read as the process starts. The app root builds its UI settings from one snapshot with one
   collector, where fifteen flows started from defaults and recomposed the tree when the real
   values arrived. When the snapshot is already in memory at `onCreate` (16 of 16 launches) the
   Activity composes Home directly instead of drawing a placeholder frame first: settings in hand
   at 50 ms, was 64.
5. **The startup gate** opens without building `ResetRepository` when no reset is pending:
   `storage.ready` 29 to 25.

## Tried and removed

- **Building the coach snapshot at launch, ahead of Home asking for it.** With eight weeks of
  history the snapshot takes about 20 ms to build and is not what Home waits for. Interleaved A/B,
  16 launches each: Home fully loaded 134 with it, 134 without. Removed. It may be worth another
  look on a history of years, where the build is longer; that needs a seeded history of that size.

## Changed without a measurement of its own

- `HubViewModel` and Home's `freestyleMode` start from the loaded settings, not from "coach on,
  planned mode". On this install both guesses were right, so nothing moved. For someone with the
  coach off or in freestyle the old defaults rebuilt the pager one emission into the launch; that
  is from reading the code, not from a timing.

## A lost data set

Between the baseline reading (18:48) and the next look at the screen (18:58) the perf install lost
its seeded history and came back onboarded differently. Reinstalling does not do this (checked
afterwards: the data survives `installPerf` and `adb install -r`), and the app has no path that
clears sessions and keeps the settings. The phone took a call at 18:52 and the perf app was in
front of its owner around then; two launches in that minute never reached Home. The cause was not
established. The history was re-seeded and every number in "Result" was taken afterwards, on one
data set, with before and after interleaved.

## Guardrails

- `ConflatedRefreshTest`: the first read of a burst starts at virtual time zero.
- `:baselineprofile`'s `StartupBenchmark` now gets a `timeToFullDisplayMs`, because Home reports
  fully drawn. It was not run here and is not in CI (it needs a device).
- No CI ratchet on launch time: CI has no device. `tools/perf/coldstart.py` is the check to run
  before a release, against the numbers above.

## Still open

- **Navigation is as long as its animation.** Every push and tab slide measured 300 to 340 ms,
  which is the Emphasized token (320); content is ready when it lands. Shortening that token is the
  only thing that would make moving around feel faster, and it is a design decision.
- **The fade.** 150 ms of the 451 on screen. A cut would bring a launch to about 300 ms.
- The journeys listed under "Not measured" in the baseline.
