### C1. SampleDataSeeder crashes onboarding for any non-4-day generated program (NoSuchElementException)

- **Where:** [data/repo/SampleDataSeeder.kt:37,44,52](forge-android/app/src/main/java/com/forge/app/data/repo/SampleDataSeeder.kt#L37)
- **Type:** crash · `repo-features-1`
- **Problem:** seed() hard-codes the day rotation to the static 4-day keys (Program.UPPER_A/LOWER_A/UPPER_B/LOWER_B = "upper-a"/"lower-a"/"upper-b"/"lower-b") and then looks each up against the *active* program with `Program.days.first { it.key == dayKey }`. In OnboardingScreen.complete(), the active program is regenerated FIRST via programRepository.generate() (which calls Program.setActive with keys derived from SplitTemplates.forDays(daysPerWeek)), and only THEN is seed() called when withSampleData is true. For any daysPerWeek != 4 the active keys are different (1->"fb", 2->"fb-a/fb-b", 3->"push/pull/legs", 5->adds "upper"/"lower", 6/7->"push-a" etc.), so `first { it.key == "upper-a" }` finds nothing and throws kotlin.NoSuchElementException, crashing the onboarding completion coroutine (and leaving onboarding not marked done).
- **Impact:** A user who picks a 1/2/3/5/6/7-day split AND enables sample data during onboarding crashes at finish; onboarding never completes (ONBOARDING_DONE is set after seed()). The same crash hits Settings -> loadSampleData() once the active program is any non-4-day split.
- **Suggested fix:** Drive the seeder off the active program instead of hard-coded keys: iterate `Program.days` (e.g. cycle `Program.dayKeys`) rather than the fixed dayRotation list, or guard each lookup with firstOrNull{} and skip unknown keys. At minimum replace `Program.days.first { it.key == dayKey }` with a null-safe lookup.

### C2. Widget opens the live DB with destructive-migration fallback — silent total data wipe on any future schema bump

- **Where:** [widget/ForgeWidget.kt:33-35](forge-android/app/src/main/java/com/forge/app/widget/ForgeWidget.kt#L33)
- **Type:** data-loss · `services-1`
- **Problem:** ForgeWidget.provideGlance opens the production database file "forge.db" with its own Room builder: Room.databaseBuilder(context, ForgeDatabase::class.java, "forge.db").fallbackToDestructiveMigration(dropAllTables = true).build(). The real app path (DatabaseModule.provideDatabase) deliberately registers addMigrations(*ALL_MIGRATIONS) and only allows destructive fallback for the pre-lock versions 1..11 via fallbackToDestructiveMigrationFrom(true, 1..11); ForgeDatabase is documented as 'schema LOCKED from v12 onward... data is never silently wiped'. The widget bypasses that entirely. The widget runs on an hourly updatePeriodMillis (forge_widget_info.xml = 3600000). After the user updates to an app build with a bumped @Database(version=N+1) + a real migration, whichever component opens the DB first performs the upgrade. If the hourly widget update fires before the user opens the app, the widget opens with the new version code but NO migrations registered and dropAllTables=true — Room drops every table and recreates the schema empty, destroying all training history, with no error surfaced. This directly defeats the project's migration-lock data-safety guarantee.
- **Impact:** Latent silent loss of the user's entire workout/cardio/program history on the first schema upgrade if the widget refresh wins the race to open the DB. Catastrophic for a personal-history app whose explicit design promise is 'never silently wipe data'.
- **Suggested fix:** Do not let the widget open the DB with a divergent config. Either obtain the Hilt-provided singleton ForgeDatabase (via an EntryPoint) so the widget shares the exact same migration-aware instance, or at minimum mirror DatabaseModule's builder exactly (addMigrations(*ALL_MIGRATIONS) + fallbackToDestructiveMigrationFrom(true, 1..11), never fallbackToDestructiveMigration(dropAllTables=true)).

## High (16)

### H1. BodyweightEntry 'one entry per day' upsert is unenforced — duplicate rows per date

- **Where:** [data/db/entities/BodyweightEntry.kt:8-16](forge-android/app/src/main/java/com/forge/app/data/db/entities/BodyweightEntry.kt#L8)
- **Type:** data-loss · `db-schema-1`
- **Problem:** BodyweightEntry's PrimaryKey is the autoGenerate `id` (Long), and `date_key` has NO unique index or constraint. The DAO (BodyweightDao.upsert, line 13-14) uses `@Insert(onConflict = OnConflictStrategy.REPLACE)`, and BodyweightRepository.log() (BodyweightRepository.kt:20-23) always constructs `BodyweightEntry(dateKey = ..., ...)` leaving `id = 0`, so Room auto-generates a brand-new rowid on every call. REPLACE only fires on a conflicting UNIQUE/PRIMARY KEY — there is none on `date_key` — so it never triggers. Logging bodyweight more than once on the same calendar day therefore inserts a SECOND row for that date instead of replacing the first. The entity KDoc explicitly promises 'one entry per day (upserted by date)', which the schema does not enforce. Downstream `latest()` (ORDER BY date_key DESC LIMIT 1) and any per-day trend/series logic then see duplicate same-day points, and editing today's weight silently accumulates rows rather than correcting the value.
- **Impact:** Bodyweight history accrues duplicate rows for any day weighed more than once; the 'edit today's weight' UX appends instead of overwriting, and same-day duplicates skew the weight trend chart and make `latest()` nondeterministic among that day's rows.
- **Suggested fix:** Add a unique index on `date_key` so REPLACE actually upserts: `@Entity(tableName = "bodyweight_entry", indices = [Index(value = ["date_key"], unique = true)])`. This requires a real migration (schema is locked from v12): bump ForgeDatabase version, add a MIGRATION_14_15 creating `CREATE UNIQUE INDEX index_bodyweight_entry_date_key` (after de-duplicating any existing same-date rows, keeping the latest recordedAt), export the new schema JSON, and add a MigrationTest case.

### H2. Restore does not validate schema version — restoring a newer-version backup crashes the app on next launch after the live DB is already overwritten

- **Where:** [data/repo/BackupRepository.kt:243-271](forge-android/app/src/main/java/com/forge/app/data/repo/BackupRepository.kt#L243)
- **Type:** data-loss · `repo-backup-prefs-1`
- **Problem:** restoreFromUri validates the candidate only with isForgeDatabase(), which merely checks that a 'session' table exists (SELECT count(*) FROM sqlite_master WHERE name='session'). It never checks the SQLite user_version against the app's Room schema version (14). The Room builder in DatabaseModule registers addMigrations(*ALL_MIGRATIONS) and fallbackToDestructiveMigrationFrom(true, 1..11) but has NO downgrade fallback. So if the user restores a backup taken from a FUTURE app build (user_version > 14), restoreFromUri happily passes validation, calls db.close(), overwrites the live forge.db with the future-version file, deletes WAL/-shm, and returns true. On the forced restart, Room opens a DB whose user_version exceeds the compiled schema with no downgrade migration and throws IllegalStateException ('Room cannot verify the data integrity / downgrade'), crashing on every launch. The previously-good database has already been destroyed, so there is no recovery path. A corrupt-but-has-session-table file is similarly accepted.
- **Impact:** Permanent data loss + unrecoverable launch crash loop after restoring an incompatible (future-version or partially-corrupt) backup. The original DB is overwritten before any version compatibility is checked.
- **Suggested fix:** Before swapping, open the candidate read-only and read PRAGMA user_version; reject (return false) if it is greater than the app's current schema version (or otherwise out of the supported migration range). Additionally, back up the existing live forge.db to a temp file before overwriting and roll it back if reopening Room fails, so a bad restore cannot leave the app permanently broken.

### H3. setSwap silently wipes the user's pinned note (rebuilds ExerciseCustomization without preserving pinnedNote)

- **Where:** [data/repo/CustomizationRepository.kt:27-33](forge-android/app/src/main/java/com/forge/app/data/repo/CustomizationRepository.kt#L27)
- **Type:** data-loss · `repo-workout-2`
- **Problem:** setSwap reads the existing ExerciseCustomization row, then constructs a brand-new instance via `ExerciseCustomization(exerciseId, swappedName, swappedUnit, restTimerOverrideSeconds = existing?.restTimerOverrideSeconds)`. It deliberately carries forward restTimerOverrideSeconds, but the entity also has a 5th field `pinnedNote: String = ""` (ExerciseCustomization.kt:23) which is NOT carried forward — the new instance gets the default empty string. Because the DAO upsert uses OnConflictStrategy.REPLACE, this overwrites the existing row and erases any pinned note the user had set via setPinnedNote. The sibling methods setRestTimerOverride and setPinnedNote correctly use `existing.copy(...)` to preserve all other fields; setSwap is the only one that rebuilds the object positionally and so drops a field.
- **Impact:** Data loss: if a user has pinned a coaching note on an exercise (#112) and then swaps that exercise, the pinned note is silently deleted. The note cannot be recovered. Any future field added to ExerciseCustomization will be dropped by setSwap too, since it doesn't use copy().
- **Suggested fix:** Use copy() to preserve untouched fields, mirroring the other setters: `val existing = customizationDao.get(exerciseId); customizationDao.upsert(existing?.copy(swappedName = swappedName, swappedUnit = swappedUnit) ?: ExerciseCustomization(exerciseId, swappedName, swappedUnit))`.

### H4. Editing reps/sets on a program exercise silently moves it to the bottom of the day (orderOverride default 999 defeats natural-order fallback)

- **Where:** [data/repo/ProgramCustomizationRepository.kt:58-64](forge-android/app/src/main/java/com/forge/app/data/repo/ProgramCustomizationRepository.kt#L58)
- **Type:** logic-error · flagged by 2 reviewers (dao-features-2, repo-workout-1)
- **Problem:** ProgramCustomization.orderOverride is a NON-null Int defaulting to 999 (ProgramCustomization.kt line 26). effectivePlanForDay sorts static exercises by `customByExId[plan.id]?.orderOverride ?: (i * 10)` (line 59). The `?:` fallback to the natural index i*10 only fires when the customization is null OR orderOverride is null — but it is never null, it is 999. setRepRange/setSetsOverride/removeExercise/restoreExercise (lines 70-92) each do `(existing ?: ProgramCustomization(dayKey, exerciseId)).copy(...)`, so the FIRST time a user edits reps or sets on a static exercise (existing == null), a fresh row is created with orderOverride = 999. That exercise then sorts at 999 — behind every un-customized exercise (orders 10,20,30,...) — and jumps to the bottom of the day. This list is consumed by DayViewModelRefresh.effectivePlanForDay (the live training screen) and the ProgramEditor, so merely changing the rep range of the first lift reorders the whole day. The DAO queries observeForDay/forDay 'ORDER BY order_override ASC' have the same root issue: every default row ties at 999, making SQL order among them nondeterministic.
- **Impact:** Any rep/set edit (or remove-then-restore) on a built-in program exercise reorders the day so the edited exercise drops to the bottom, corrupting the workout order the user actually trains in. Reproducible on the first edit of any static exercise.
- **Suggested fix:** Treat 999 as 'no explicit order' in the sort, e.g. `customByExId[plan.id]?.orderOverride?.takeIf { it != 999 } ?: (i * 10)`; or change orderOverride to a nullable Int? defaulting to null so the existing `?:` fallback works; or have setRepRange/setSetsOverride/removeExercise seed orderOverride from the exercise's natural index when creating a brand-new row.

### H6. parseToLb cannot round-trip formatWeight output: tapping a kg suggestion logs a set with no weight

- **Where:** [domain/units/WeightFormatter.kt:15-18](forge-android/app/src/main/java/com/forge/app/domain/units/WeightFormatter.kt#L15)
- **Type:** data-loss · `domain-1`
- **Problem:** formatWeight ALWAYS appends a unit suffix (" kg" / " lb"), but parseToLb parses with a bare input.toDoubleOrNull(). Any string produced by formatWeight therefore fails to parse back: parseToLb("20.4 kg", true) -> "20.4 kg".toDoubleOrNull() == null -> returns null. The kg autofill path exercises exactly this: in SetInputRow (components/SetInputRow.kt:211) tapping the prior-set 'try X' hint sets the weight field to formatWeight(weightLb, useKg) = e.g. "20.4 kg". On submit, DayContent.onLogSet (DaySessionContent.kt:170-173) calls parseToLb("20.4 kg", true) which returns null, so storedWeight falls back to the raw "20.4 kg" string, which WeightParser.parse() also cannot parse (it has no kg handling) and returns null. The set is stored as bodyweight (weightLb = null) and contributes 0 to volume and never counts as a PR. The lb path is unaffected only because WeightParser happens to tolerate a ' lb' suffix; the kg path is broken. parseToLb should strip a trailing unit label (and/or formatWeight should expose a unit-less numeric form for re-entry).
- **Impact:** In kg display mode, tapping the 'try' / autofill suggestion (a common quick-log action) logs the set with no weight: volume undercounts, PR detection misses, and the user's actual load is silently lost. Edit-set re-entry of a displayed kg value has the same failure.
- **Suggested fix:** Make parseToLb tolerant of the unit suffix it pairs with formatWeight, e.g. val numeric = input.trim().removeSuffix("kg").removeSuffix("lb").trim().toDoubleOrNull() ?: return null. Better: have the autofill/edit paths re-emit a unit-less numeric string instead of the display-formatted string.

### H7. Foreground service started with FOREGROUND_SERVICE_TYPE_HEALTH but lacks the required runtime permission — SecurityException on Android 14+ (targetSdk 35)

- **Suggested fix:** Switch the FGS type to one whose prerequisites the app actually satisfies — e.g. FOREGROUND_SERVICE_TYPE_SPECIAL_USE (manifest foregroundServiceType="specialUse" + a <property> subtype and the FOREGROUND_SERVICE_SPECIAL_USE permission). ### H8. Notes search field lags / drops characters — TextField value driven by a debounced async flow

- **Where:** [ui/gym/notes/NotesSearchViewModel.kt:32-42](forge-android/app/src/main/java/com/forge/app/ui/gym/notes/NotesSearchViewModel.kt#L32)
- **Type:** ui-state · `trophies-recap-notes-history-1`
- **Problem:** The screen binds `OutlinedTextField(value = state.query, onValueChange = viewModel::setQuery)`. `setQuery` only updates the private `_query` flow; the public `state` (and therefore `state.query`) is produced downstream of `_query.debounce(300).flatMapLatest { search() }.map { NotesSearchUiState(query = _query.value, results = results) }`. Because a new `NotesSearchUiState` is emitted only AFTER the 300ms debounce and the suspend DB query complete, the text shown in the field does not update on each keystroke — it updates ~300ms+ after typing pauses, and the emitted `query` is whatever `_query.value` happens to be at emission time (not the debounced `q`). With a controlled TextField whose displayed value is this lagging state, fast typing visibly stutters / appears to drop or reorder characters, and the cursor jumps.
- **Impact:** Core search input feels broken: typing is laggy and characters appear to drop because the field's displayed value only refreshes on debounced async emissions instead of immediately reflecting keystrokes.
- **Suggested fix:** Drive the TextField from an immediate snapshot/StateFlow that `setQuery` updates synchronously (e.g. expose `query` from `_query` directly, or hold a separate `mutableStateOf`/StateFlow for the raw text), and use the debounced flow ONLY to compute `results`. Don't read `_query.value` inside `.map` — combine the raw query state with the debounced results so query text and results are consistent and the field updates instantly.

When successive points are far apart in value (long diagonal segments), a dot can appear before or after the drawn line reaches it. Driving both off the same arc-length progress (e.g. cumulative segment length / total length) would make the reveal visually consistent. Cosmetic only. ([ui/gym/history/SessionHistoryViewModel.kt:](forge-android/app/src/main/java/com/forge/app/ui/gym/history/SessionHistoryViewModel.kt))
- **Onboarding has no input validation / progress guard** — The onboarding 'Next' button is always enabled; a user can leave the name blank (stored as empty, completeOnboarding only sets USER_NAME if non-blank, so the greeting falls back) and can advance past the bodyweight step with garbage that toDoubleOrNull() silently drops to null. ([ui/onboarding/OnboardingScreen.kt:](forge-android/app/src/main/java/com/forge/app/ui/onboarding/OnboardingScreen.kt))
